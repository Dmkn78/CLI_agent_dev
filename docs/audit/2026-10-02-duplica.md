# Duplica Agent — livraison du 2 octobre 2026

Duplica est une capacité native d'Atelier : contexte et décisions persistants,
supervision par périmètre, interventions dans l'interface, vérifications
indépendantes, rapports de bugs et corrections bornées. Le MVP a été exécuté
avec un fournisseur fictif puis avec **GPT-6-Luna** dans un projet synthétique.

Les [deux demandes intégrales](../references/2026-10-02-duplica-mission.md) et
leur [complément d'intégration](../references/2026-10-02-duplica-platform.md)
sont archivés. Les skills utilisés sont `engineering-workflow`,
`clean-code-workflow`, `coding-rules` et `code-quality`. Les consignes Computer
Use ont également été consultées pour la recette ; le produit réutilise
Electron, aucun contrôle Windows externe n'a été prétendu exécuté.

## Comportement livré

- Indicateur Duplica dans la barre principale, manager transversal, timeline,
  contextes global/projet, décisions, demandes, missions, observations et preuves.
- Activation globale, projet, workflow, tâche et session ; héritage remplacé
  par la portée la plus locale. Les benchmarks sont exclus. Aucune activation
  ni inférence au premier lancement ; sélectionner un périmètre reste explicite.
- Réponse aux formulations exactes enregistrées, avec provenance de la décision.
  Une réponse contradictoire, inconnue ou sensible demande l'utilisateur.
- Politiques `auto`/`ask`/`deny`, classification conservatrice des commandes et
  confinement des chemins. `on-request`, lecture seule, écriture projet et
  validation humaine des plans sont conservés. Aucun bypass de sandbox.
- Captures PNG réelles, contrôles observés, clics, double clics, clavier,
  défilement et navigateur local isolé. Le canal d'intervention est enregistré ;
  le mode « interface obligatoire » ne se rabat pas silencieusement sur l'API.
- Recette définie par l'utilisateur : fichiers/contenu, tests, build ou absence
  déclarée de compilation, application locale, étapes GUI et résultat visible.
  Les commandes exécutées, sorties, codes de retour, captures et hashes sont
  enregistrés indépendamment des déclarations de l'agent.
- Rapport de bug envoyé au même agent, depuis l'implémentation existante ;
  maximum 0 à 10 relances. Les bugs résolus pointent vers le retest réussi.
- Pause, Stop et reprise du contrôle annulent les actions en attente. Le
  watchdog demande un diagnostic après silence/crash, sans redémarrage aveugle.
  Au redémarrage, reprise explicite et conservation de l'état/provenance.
- Relais Telegram facultatif : compte privé autorisé, offset persistant,
  décisions ponctuelles, commandes et instructions libres mémorisées, événements
  importants uniquement. Le token reste dans l'environnement du service.

`Vérifiée` signifie que la recette enregistrée a réussi. La tâche du tableau
reste **En revue** ; elle n'est pas marquée Terminé à la place de l'utilisateur.
La file existante garde le bail de la tâche pendant les corrections et tests.

### Démonstration avec fournisseur fictif et vrai contrôle GUI

Le scénario impose une permission `npm test`, puis une question de format.
Duplica observe les demandes dans Atelier, clique sur Autoriser, sélectionne le
champ, saisit CSV depuis la décision enregistrée et valide. Aucun endpoint de
réponse n'est appelé par le script de recette pour contourner ces interactions.

L'agent produit une page d'export volontairement cassée et omet un fichier
attendu. Duplica exécute un vrai sous-processus de test, lance le serveur HTTP,
ouvre sa fenêtre, saisit un nom, clique Exporter et constate « Erreur export ».
Les deux corrections successives sont demandées et le troisième contrôle passe.
La reprise du contrôle bloque ensuite toute nouvelle continuation.

Preuves privées de la recette finale :

- `.atelier/duplica-e2e/run_168d2eb805ae/acceptance.json`
- `.atelier/duplica-e2e/run_168d2eb805ae/manager.png`
- Rapports, sorties et captures dans `data/duplica/` sous ce même dossier.

Ces données sont isolées et ne remplissent pas le cockpit réel de Damien.

### Démonstration Codex réelle

Le modèle exact **gpt-6-luna**, avec effort découvert, est choisi via
`model/list`. Aucun fallback. Codex utilise son authentification native ; aucun
credential n'est lu ou copié. La mémoire Atelier est désactivée et le dossier
de travail synthétique est extérieur au dépôt : aucun contexte personnel ou
document de ce projet n'est transmis par la recette. La configuration native
du fournisseur peut toutefois charger ses propres outils/consignes.

Le premier tour crée une page HTML avec un défaut contrôlé et le test unittest,
sans `receipt.txt`. Duplica constate les deux écarts, transmet le rapport, puis
Codex corrige. La nouvelle recette vérifie le fichier, exécute le test avec
code de sortie 0 et observe « Export réussi » après le clic et la saisie réels.
La page HTML ne nécessite pas de compilation : `buildNotApplicable` est
déclaré explicitement ; aucun succès de compilateur n'est prétendu.

Cette session réelle n'a posé ni question ni demande de permission. Ces deux
branches sont couvertes par le scénario fictif précédent, sans les attribuer
au modèle réel. Telegram n'était pas configuré ; aucun message réel n'a été envoyé.

Preuves privées :

- `.atelier/duplica-e2e/run_7c2427fc9fdf/acceptance.json`
- Premier contrôle : `verification_673461683e4b`, échec requirements et GUI.
- Retest : `verification_e2bdd1b716c4`, tous les contrôles exécutés réussis ;
  SHA-256 des octets du fichier de rapport :
  `a0403a2708afa86332ec11a351d8b95276f93055e518bc959c1f7336ec96008b`.
- Capture finale :
  `data/duplica/screenshots/screen_64f199d1187d.png` sous ce dossier ; SHA-256 :
  `4ea888fa9cf41de24c590a451a09fc0a49cc4d55708de10115dc9afff2c8f516`.

Les preuves historiques de cette session sont conservées telles quelles. Leur
champ `artifact.sha256` avait été calculé sur le JSON UTF-8 avec fins de ligne LF,
alors que Windows écrivait CRLF : l'empreinte annoncée du retest était
`44c05febad8e5f40ec2cea2904a940342d03ed719b978ea5d102a8de8e5fdd2f`.
Les résultats de tests et de GUI restent consultables ; les captures PNG avaient
déjà une empreinte exacte. L'écriture binaire corrige désormais cet écart pour
les nouveaux rapports, sorties et artefacts de session. Les tests et la recette
Electron finale recalculent les hashes depuis les fichiers enregistrés.

## Corrections issues de la recette

1. Attendre l'initialisation et l'apparition des demandes. Le rafraîchissement
   de la plateforme peut précéder ou suivre un événement de Codex.
2. Ne pas cliquer derrière une fenêtre modale. Révéler un contrôle hors écran
   avant de cliquer ; arrêter l'attente après un délai borné.
3. Revalider l'identité, la position, le focus et la génération de l'action.
   Seul le refus typé **avant émission** du clic permet une observation et une
   nouvelle tentative. Un résultat indéterminé après action ne se rejoue pas.
4. Consommer l'accord avant que le fournisseur puisse émettre sa demande
   suivante, afin de préserver le nouvel état et d'empêcher une double réponse.
5. Distinguer une preuve inaccessible d'un défaut du code. Un premier essai réel
   a révélé une ACL temporaire Windows avec `OWNER RIGHTS` : l'agent pouvait lire
   le HTML, mais le compte du serveur de recette ne le pouvait pas. Le vérificateur
   doit demander l'intervention, sans relancer l'agent pour ce problème d'accès.
   Le nouveau dossier synthétique hérite d'un accès pour son seul compte créateur ;
   aucune ACL du projet ou restriction du sandbox n'est modifiée.
6. Conserver la définition de recette et son identité. Un résultat arrivant après
   modification des critères ne valide pas la nouvelle mission ; les anciens
   bugs remplacés par l'utilisateur ne sont pas déclarés corrigés.
7. Permettre au fil d'Ariane de rétrécir avec le nouveau bouton global, pour
   préserver les actions à 300 pixels. Cibler la fenêtre Atelier dans les captures
   de manager, distincte de la fenêtre d'application créée par Duplica.
8. Attacher les flux natifs du PTY et rendre le terminal avant de lancer les
   requêtes de métadonnées Duplica. La recette desktop finale vérifie le démarrage,
   l'echo, la sortie et sept terminaux simultanés ; les tentatives précédentes
   avaient échoué ou attendu au démarrage du PTY fictif.
9. Écrire les preuves en octets UTF-8 et calculer leur SHA-256 sur ces mêmes
   octets. La conversion implicite LF/CRLF de Windows ne doit pas produire
   d'empreinte différente du fichier, ni doubler les retours dans les sorties.

Ces comportements sont couverts par les tests de régression. Les essais
intermédiaires et leurs preuves restent conservés dans les données privées.

## Reproduire

Tests ordinaires, sans inférence :

```powershell
$env:PYTHONDONTWRITEBYTECODE='1'
python -m unittest discover -s tests -v
node tests/test_cockpit.cjs
```

Avec Playwright disponible, lancer `python -B tests/browser_fixture.py`, puis
`node tests/duplica_browser_acceptance.cjs`. Chrome installé peut être choisi
avec `ATELIER_BROWSER_CHANNEL=chrome`. Chaque démarrage du serveur possède ses
données de recette isolées ; redémarrer entre les recettes générales.

Pour Electron, lancer `python -B tests/duplica_fixture.py`, puis
`node tests/duplica_acceptance.cjs`. Le fournisseur est fictif par défaut. Ports
4328/4329, fermeture des processus et fenêtres appartenant à la recette.
Sur cet environnement Windows, Electron a nécessité une exécution hors du
sandbox de l'outil, tout en conservant `sandbox: true` pour ses renderers.

La variante `--real-model MODELE_EXACT` exige une autorisation explicite de
consommer du quota, un modèle découvert et une connexion native. Elle crée
uniquement des fichiers synthétiques dans un répertoire temporaire, conservé
avec les preuves. Le certificat public Windows est fourni au processus Codex
par l'environnement ; aucun contournement TLS n'est utilisé.

## Limites explicites

- Le contrôleur livré agit dans **Atelier et le navigateur HTTP local**.
  Excel, l'IDE externe, GitHub dans un navigateur distant, les fenêtres système
  et le contrôle universel du poste nécessitent un autre adaptateur.
- **Sessions outillées** : supervision sémantique Codex/plateforme.
  **Terminaux natifs** : processus et activité uniquement ; leurs popups,
  questions et états de mission ne sont pas inférés depuis la sortie du PTY.
- Les réponses automatiques reposent sur des décisions exactes/alias enregistrés,
  pas sur un modèle prédictif avancé de l'utilisateur. Le contexte libre est
  transmis aux missions, borné à 4 000 caractères.
- Les parcours GUI sont explicites. La détection générale de problèmes UX par
  raisonnement visuel, l'exploration libre et les recettes Excel restent ouvertes.
- Les commandes de recette tournent dans le dossier du projet, sans shell
  intermédiaire, avec les droits du serveur local. Ce n'est pas une nouvelle
  sandbox OS ; elles doivent être choisies par l'utilisateur.
- Telegram est implémenté et testé avec transport fictif. Son fonctionnement
  réseau, les notifications et les captures avec un bot réel restent à valider
  après configuration par l'utilisateur.
- La reprise évite de rejouer des effets incertains. Elle ne reconstruit pas
  automatiquement toute application externe ni tous les processus après reboot.
- Cette démonstration courte ne prouve pas une autonomie ininterrompue pendant
  plusieurs heures, ni la validité d'une recette qui omet un critère métier.

Le code est dans le checkout actuel. Aucune publication, campagne réelle de
benchmark, push ou création de PR n'a été effectué pour cette livraison.
